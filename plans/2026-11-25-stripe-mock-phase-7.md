# Stripe Mock Phase 7 (Generated Types and Payments Core) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every object the mock serves is built from Rust types generated from the vendored Stripe OpenAPI spec, and the mock gains the payments core: payment intents, charges, refunds, disputes, balance transactions, payment methods, setup intents, Checkout sessions and invoice payments.

**Architecture:**
- **Vendored spec, committed generated code.** `crates/stripe-mock/openapi/spec3.json` is the source. A generator in the crate's test tree turns an allowlist of root schemas, plus their non-expandable closure, into `src/stripe/generated/`.
  - The integration test `openapi_codegen` regenerates the code in memory and fails if the committed files differ.
  - Run with `DUCTKIT_REGEN=1`, the same test rewrites the files instead.
- **The store stays JSON, but only typed code writes it.**
  - `Engine` gains typed `create_obj`, `update_obj` and `latest_obj` helpers. The `Value`-closure `update` becomes private once every model is converted, so the compiler enforces the rule.
  - Generated structs derive no `Default`, so every constructor names every field.
- **A conformance check proves nothing slipped past the types.** `ductkit_stripe_mock::stripe::check_payload` deserializes any served payload into its generated type, with unknown fields denied.
  - The shared test helper `common::get` runs it on every 2xx body.
  - A dedicated coverage test runs it on everything a busy Connect run serves.
- **Payments are new object types handled by the existing engine** (truth log, scopes, events, faults and history are unchanged). A new RNG stream, `"generate.payments"`, keeps billing draws where they were.

**Tech Stack:** The phase 6 stack, plus:
- `serde_path_to_error`, so conformance errors name the failing field path;
- the dev-dependencies `syn` (with the `full` feature), `quote`, `proc-macro2` and `prettyplease`, for the generator.

**Spec:**
- The design: [docs/superpowers/specs/2026-11-25-stripe-mock-types-and-openapi-design.md](../docs/superpowers/specs/2026-11-25-stripe-mock-types-and-openapi-design.md), the binding authority for this plan. Phase 7 covers its sections 6.1–6.4, group 1 of 6.5, the phase-7 parts of 6.6, and section 7.
- The project spec: [docs/stripe-mock-spec.md](../docs/stripe-mock-spec.md), sections 4, 5, 6.1, 7, 8, 14 and 16.

## Global Constraints

Not from tag `v2602`.
- **Regenerate command:** `DUCTKIT_REGEN=1 cargo test -p ductkit-stripe-mock --test openapi_codegen`. The freshness failure message prints it verbatim.
- **Generated code** lives in `crates/stripe-mock/src/stripe/generated/`, starts every file with `// @generated by tests/codegen from openapi/spec3.json — do not edit; regenerate with: <command>`, is skipped by rustfmt, and is never hand-edited.
- **Type mapping** (design 6.2, amended by Ruling R1 below):

  | Spec field | Rust type |
  |---|---|
  | required, not nullable | `T` |
  | required, nullable | `Option<T>`, always serialized |
  | not required, not nullable | `Option<T>`, skipped when `None` |
  | not required, nullable | `Option<Option<T>>` (outer `None` = absent, `Some(None)` = `null`) |

  Generated structs and enums derive `Serialize, Deserialize, Clone, Debug, PartialEq`, structs add `#[serde(deny_unknown_fields)]`, and **none derives `Default`**.
- **Only typed code writes objects.** Model and generator code builds and changes objects only through the generated structs. Free-form `serde_json::Value` is allowed only where the schema itself is free-form.
- **The pinned schema wins.** When it disagrees with documented behavior or an existing test, follow the schema. Update that test and the spec section in the same task, and ledger it as a ruling.
- **Determinism:** same seed and config give the same run. New draws come from new streams (`"generate.payments"`, plus one per new Poisson action). New `ActionKind` variants are appended at the end. Exports from before this phase need not replay identically.
- **Config:** new action and churn keys default to 0. Payment objects on invoice payment are always on. The `UNIMPLEMENTED_KEYS` entry for `one_off_payment`, `refund` and `dispute` is removed. The example TOML in `docs/stripe-mock-spec.md` section 4 is parsed by a config test, so it must stay valid.
- **Dependencies:** versions only in the root `[workspace.dependencies]`. Generator crates are dev-dependencies only.
- **Process:**
  - `cargo fmt --all`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` run as separate steps before each commit.

## Rulings made while planning

- **R1, presence of optional fields.** The spec's `required` lists don't say which fields are present. `customer` marks only `created, id, livemode, object` as required, yet real responses always carry `email`. The generator therefore can't decide absent versus `null`. It maps fields as in the table above, and the model code decides presence explicitly for every field: no `Default`, and no `..` struct update from a default.
  - Rule for model code: a field that is not required is present (`Some`, or `Some(None)` for `null`) unless Stripe documents it as includable-only or expandable-only. Those fields (such as `customer.sources`, `customer.subscriptions` and `customer.tax`) are `None`.
  - Cost if wrong: an always-present field left absent gets past the round-trip check. Review Focus item 1 targets it.
- **R2, `deleted: true` in deleted-event payloads.** The mock adds `deleted: true` to the `data.object` of deletion events. No live schema has `deleted` (only `deleted_*` schemas do), so the schema wins: `data.object` of a `*.deleted` event is the last live object, unchanged. Cost if wrong: a consumer keying on `data.object.deleted` breaks, but real Stripe doesn't send it either.
- **R3, the conformance check lives in the library.** It is `pub mod stripe` with `check_payload`, so integration tests and the coverage test can call it. The generated types become public API of the mock crate. That's fine, because nothing outside the mock depends on the mock.

## Review Focus

1. **An always-present field is left absent** (R1). Example: a `charge` without `outcome`, or an invoice without `payments`. A sync user's mapping to that column would silently get NULL. Test `served_objects_carry_their_documented_fields` (Task 13) asserts, for each phase-7 type, the field set the model serves on a fresh object against a list taken from Stripe's API reference: every field not documented as includable or expandable-only.
2. **A payment's objects disagree with each other.** For example, the charge amount differs from the payment intent's `amount_received`, the invoice's `amount_paid` differs from its `invoice_payment.amount_paid`, a balance transaction's `net` doesn't equal `amount - fee`, or a refund total exceeds the charge. Test `payment_objects_are_consistent` (Task 13) walks a busy run and checks each invariant.
3. **A Connect run puts payment objects in the wrong scope.** A connected account's invoice payment must create its payment intent, charge, balance transaction and invoice payment in that account's scope, labelled with the account in events. Test `connected_payments_stay_in_scope` (Task 9).
4. **A balance transaction changes with no event**, and a consumer that only listens to webhooks never sees it. The mock must change `status` exactly at `available_on`, and must not emit an event, so a re-list shows `available`. Test `balance_transaction_becomes_available_silently` (Task 9).
5. **Stale reads and pagination writes on the new lists.** `/v1/charges` and `/v1/payment_intents` under `stale_read` and `pagination_writes` must page without duplicates or resurrection, like the existing lists. Test `payment_lists_survive_faults` (Task 13).

- Produces (in `tests/codegen/names.rs`):
  - `pub fn type_name(schema: &str) -> String`: `checkout.session` → `CheckoutSession`, `v2.core.account` → `V2CoreAccount`, `line_item` → `LineItem`.
  - `pub fn field_name(json: &str) -> String`: snake case, with Rust keywords suffixed `_` (`type` → `type_`).
  - `pub fn variant_name(value: &str) -> String`: CamelCase. A value starting with a digit gets a `V` prefix (`3d_secure` → `V3dSecure`). The empty string becomes `Empty`.
- Rules `build_ir` implements:
  - Roots plus the closure over non-expandable `$ref`s.
  - A field is expandable if it is in the parent's `x-expandableFields` and is an `anyOf` containing `{type: string}`.
    - Its targets are the `$ref`s in the `anyOf`.
    - If at least one target is in `roots`, the field is `Expandable(inner)`. `inner` is that single target, or a generated `Union` named `{Parent}{Field}` over the root targets. Targets that aren't roots are dropped from the union.
    - If no target is in `roots`, the field is `IdOnly`.
  - An inline object schema with `properties` becomes a struct named `{Parent}{Field}` (CamelCase). An object with only `additionalProperties` becomes `Map(value)`. One with neither becomes `Json`.
  - A list wrapper becomes `List(item)`: an object with `object.enum == ["list"]` and a `data` array.
  - `format: unix-time` and integer types become `I64`, `number` becomes `F64`, and `format: decimal` becomes `String`.
  - Any other `anyOf`/`oneOf` becomes a `Union` named `{Parent}{Field}`.
  - A one-value string enum on a field named `object` sets `StructDef.object`, and the field's type becomes a generated single-variant enum.
  - Name collisions return `Err` naming both schemas. No silent renaming.

### Task 4: Conformance check and typed engine helpers

**Files:**
- Create: `src/stripe/conformance.rs`
- Modify: `src/engine/mod.rs`, `tests/common/mod.rs`
- Test: `tests/conformance.rs`

**Interfaces:**
- Consumes: the generated `check_by_object` and `schema_fields` (Task 3).
- Produces:
  - `pub fn check_payload(v: &serde_json::Value) -> Result<(), ConformanceError>` (in `ductkit_stripe_mock::stripe`). It dispatches on the payload's shape:
    - `object == "list"` checks every `data` item.
    - A v2 list (has `next_page_url`) checks every `data` item.
    - `object == "event"` checks the envelope as `event`, then `data.object` recursively, then requires every `data.previous_attributes` key to be in `schema_fields` of `data.object`'s schema.
    - `object == "v2.core.event"` checks as `v2.core.event`.
    - An `error` envelope checks as `error`.
    - `deleted: true` checks as `deleted_<object>`.
    - Anything else is checked by its `object`.
    - An unknown `object` is an error.
  - `pub struct ConformanceError { pub object: String, pub path: String, pub message: String }`, which implements `Display`.
  - `pub(crate) fn create_obj<T: Serialize>(&mut self, t: ObjectType, id: String, obj: &T, cause: Cause, events: &[&str]) -> StateUpdate`
  - `pub(crate) fn update_obj<T: Serialize + DeserializeOwned>(&mut self, t: ObjectType, id: &str, f: impl FnOnce(&mut T), cause: Cause, kind: ChangeKind, events: &[&str]) -> Result<Option<StateUpdate>, MockError>`
  - `pub(crate) fn latest_obj<T: DeserializeOwned>(&self, t: ObjectType, id: &str) -> Option<T>`
  - `update_obj` deserializes the latest state. A failure is a bug, so it panics with the type, the ID and the path.
  - `tests/common`: `pub const CONFORMANCE_CHECKED: &[&str]` (object values whose payloads `get` checks; empty in this task, and each later task appends to it), and `pub fn assert_conforms(v: &Value)`. `get`, `get_with`, `get_as` and `get_ctx` buffer the body, and on 2xx with a JSON body they run `check_payload` on every object in it whose `object` is in `CONFORMANCE_CHECKED`, recursing into lists and events. They then return a response rebuilt from the buffered bytes, so callers' `.json()` and `.text()` still work.

**Interfaces:**

- Produces:
  - `pub(crate) struct PaymentOutcome { pub payment_intent: String, pub charge: String, pub balance_transaction: Option<String>, pub invoice_payment: Option<String> }`
  - `pub(crate) fn pay_invoice(engine: &mut Engine, ctx: &mut Ctx, invoice: &str, succeed: bool, cause: &Cause) -> PaymentOutcome`
  - `pub(crate) fn charge_once(engine: &mut Engine, ctx: &mut Ctx, customer: Option<&str>, amount: i64, currency: &str, succeed: bool, cause: &Cause) -> PaymentOutcome`: the shared core, which `one_off_payment` (Task 10) also uses.
  - `pub(crate) fn ensure_payment_method(engine: &mut Engine, ctx: &mut Ctx, customer: &str, cause: &Cause) -> String`: the customer's newest attached card payment method, or a new one created and attached (`payment_method.attached`).
- Order of mutations for a successful invoice payment. Each step is one `create_obj` or `update_obj`, with the events in brackets. All share the action's cause and run in the same simulated instant, in this order:
  1. `ensure_payment_method` (`payment_method.attached` only if created)
  2. create the payment intent, `status: requires_confirmation` (`payment_intent.created`)
  3. create the balance transaction, `type: charge`, `status: pending`, `available_on` = created + 2 days, fee = 2.9% + 30 in the minor unit, rounded half up, and 0 for zero-amount (no event)
  4. create the charge, `status: succeeded`, `paid: true`, `captured: true`, `balance_transaction` set (`charge.succeeded`)
  5. update the payment intent to `status: succeeded`, `latest_charge`, `amount_received` (`payment_intent.succeeded`)
  6. create the invoice payment, `status: paid`, `payment.type: payment_intent` (`invoice_payment.paid`)
  7. today's invoice `paid` mutation, now also appending the invoice payment to `invoice.payments` (`invoice.paid`, `invoice.payment_succeeded`)
- On failure (the existing `payment_failure_probability` draw stays on `ctx.billing`, so the draw order is unchanged):
  1. `ensure_payment_method`
  2. create the payment intent (`payment_intent.created`)
  3. create the charge, `status: failed`, `failure_code: card_declined`, no balance transaction (`charge.failed`)
  4. update the payment intent to `status: requires_payment_method`, `last_payment_error` set (`payment_intent.payment_failed`)
  5. today's invoice failure mutation (`invoice.payment_failed`)

  A retry of the same invoice reuses its payment intent: a new charge, then `succeeded` or `payment_failed` again. An invoice voided or marked uncollectible after a failure cancels its payment intent (`payment_intent.canceled`, `cancellation_reason: void_invoice`).
- **Silent availability.** Creating a `pending` balance transaction schedules `Continuation::BalanceAvailable { id }` at `available_on`. It changes `status` to `available` with `events = &[]`.
- **Connect.** A connected account's generator runs this same flow in its own scope. That is a direct charge, and phase 8 adds the application fee and the platform patterns. Nothing is labelled differently.
